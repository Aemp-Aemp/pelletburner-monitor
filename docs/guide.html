Pellet burner monitor — guide

Version 2026-11-22For the monitor software and controller software V1.30.15 – 1.41

Unofficial — use at your own risk

This is a hobby project. It is not made, checked or supported by the boiler's manufacturer. Everything about the controller comes from watching the boiler and its module port, and may be wrong for your boiler or software version.

Never bypass safety devices (THERMOSIKRING, sensors, fuses, alarms). Keep the boiler's own safety functions on, and let a person look at an alarm before the boiler is restarted. The program never resets alarms by itself unless you switch that on. Switch the boiler off before touching the board: part of it carries 230 V.

The same short notice is at the bottom of both web pages.

The guide has two parts. The monitor software explains how to install and run the program on a Raspberry Pi. The rest describes the boiler controller itself: how it works, alarms and troubleshooting, the J4 port, its protocol, tools and open questions. Items marked (unconfirmed) or (not tested) have not been checked on a real boiler.

Easy install (Raspberry Pi, no typing)

  1. In Raspberry Pi Imager choose Raspberry Pi OS Lite (64-bit). In Imager's settings set the host name pelletpi, a user name and password, your Wi-Fi and your time zone. Write the card.
  2. Unzip pelletpi-card.zip (from the releases page) onto the card's boot drive (bootfs): the folder pelletpi and the file vendor-data. If the drive is gone after writing, take the card out and put it back.
  3. Put the card in the Pi, plug the USB adapter into the boiler's module port, and switch the Pi on.
  4. Wait about 15 minutes, then open http://pelletpi.local on your phone or PC (same Wi-Fi).

The Pi needs internet the first time; without it, it waits and tries again every minute. To see progress, open http://pelletpi.local while it installs, or put the card in a PC and open pelletpi-status.txt. Every night it installs a new release by itself, but only while the burner is off or waiting (turn off: AUTO_UPDATE=no in pelletpi/settings.txt). The page also has a Check for update button: see Updating.

Wi-Fi typo or a new router? No PC needed. When the Pi has no network for 3 minutes, it opens the Wi-Fi pelletpi-setup (no password). Join it with your phone, open http://10.42.0.1:8099, pick your Wi-Fi and type its password. The hotspot turns off when the Pi is on your Wi-Fi, or after 15 minutes. A network cable to the router works too. New, not tested on a real Pi.

New

The easy install and the auto-update are not tested on a real card yet. Details for maintainers are in pi/README.md.

The monitor software

A small program and web page for a home pellet burner. It listens on the burner's module port (J4), saves the history, and shows it on a friendly page (English or Danish) on your phone or PC:

  • what the burner is doing right now, with a live picture of the fire;
  • a heating plan: "warm by 05:30", "keep warm 17:15–19:30", "start at 09:00". Under the plan: was the boiler warm in time the last mornings, and how many kg of pellets each period uses a day;
  • pellets left at home, ash bin fill level, burner health compared with its own normal;
  • history charts (short burns under 30 min show as the light part of "Starts per day"), lighting times per start and per pellet batch (names that differ only in case or spaces are one batch; when the boiler type setting changes, the "usual" lighting times start again), outside temperature (optional);
  • Share my burner (on History): one picture with your burner's numbers (lighting time, burns and pellets per day, alarms, health) to post in a group. It holds no place, names or pellet brand, and nothing is uploaded: the picture is saved on your phone or PC. Picture for service next to it makes a tall picture for troubleshooting help: settings against factory, the last 10 starts, flame and fan by power, burn lengths, boiler temperature, ash plate turns, alarms and data gaps. The first time, it asks for three numbers the boiler does not send (software version, MIN YDELSE, fan rpm at 100 %); they are kept on the monitor (change them in Settings → My boiler) and never sent to the boiler. Skip is fine.

It runs offline. Only the optional outside temperature uses the internet (Open-Meteo, no account). The program never resets alarms by itself unless you switch that on.

The Now page on a PC and on a phone (dark theme). More pictures are in the README.

What you need

  • A Raspberry Pi 4 (or any Linux PC) with Docker.
  • A USB-RS-485 adapter with automatic direction control (FTDI, CH340, CP210x and similar).
  • A network cable with one end cut off: J4 pin 1 (white-orange) to B (D−), pin 2 (orange) to A (D+), pin 3 (white-green) to GND. Tape off the other wires. Pictures in Communication port (J4).
  • The burner set to allow a remote module: AVANCERET → EKSTRA UDSTYR → IO BOKS on.

Which controller software is supported

  • Works with controller software 1.30 or newer (from 2018). It has the Wi-Fi / IO box connection the monitor uses. Tested on 1.40 (the maintainer's boiler). 1.40.1 and 1.41 use the same connection and should work; 1.41 only adds a cloud address for the Wi-Fi module (not tested live yet).
  • Not supported: software older than 1.30, for example 1.13 (2015). It has no Wi-Fi / IO box connection at all, only the old SMS box link. Updating the controller software is a job for the dealer. Before and after an upgrade: see After upgrading the boiler's software.
  • Boiler types: the controller knows three: 10 kW (shown as "1200GP" from 1.40), 15 kW ("1700GP") and 25 kW. The monitor works with all three. The type is set on the boiler itself (MONTØR → KEDEL TYPE); set the monitor's boiler size (Settings → My boiler) to match.
  • Hardware: these software versions run on hardware V3 and V4. The INFO menu shows both versions: MENU → FLERE → INFO.

Quick start (Docker)

git clone https://github.com/Aemp-Aemp/pelletburner-monitor.git
cd pelletburner-monitor
docker compose up -d --build

Or all in one on a fresh Raspberry Pi OS: after cd pelletburner-monitor run sudo sh pi/install.sh. It installs Docker, starts the monitor and sets up the page on port 80, Pi health logging and the safe nightly auto-update. Then open http://pelletpi.local. Safe to run again; leave a part out with NO_PORT80=1, NO_LOGGING=1 or NO_UPDATE=1.

Open http://pelletpi.local:8787 (or http://<pi-address>:8787) in a browser on the same network. To drop the :8787, run sudo sh pi/enable-port-80.sh once; then it is just http://pelletpi.local. The older, more technical page is at /classic.

  • Serial port: found by itself when one USB-serial adapter is plugged in. See "Connecting the boiler" below.
  • Data: history, settings and pellet counts are kept in ./data and survive updates.
  • Who can use the buttons: BURNER_ALLOWED_HOSTS (default lan,pelletpi.local) lists the addresses the page may be opened under. lan means any private IPv4 address on your home network. Everyone who can reach those addresses can use the buttons, so keep the Pi on a network you trust.
  • Settings: copy .env.example to .env next to docker-compose.yml, remove the # in front of what you want to change, then docker compose up -d. No code needs to be edited. You can set the page port, view only (BURNER_REMOTE_START=0: no start/stop), days of history kept, log size, the serial adapter and Home Assistant.

First start: the setup guide

The first time the page is opened on a new monitor, it shows a short step-by-step guide instead of the normal page. Every step has Back, Skip and Next, and everything can be changed later in Settings. The answers are kept on the monitor, so every phone and PC sees them. The guide never starts, stops or changes the boiler. To see it again: Settings → Service & relearn → Run the setup again.

  1. Language: English or Danish.
  2. Welcome: shows live if the boiler is connected. If not, check the cable and that the boiler has EKSTRA UDSTYR → IO BOKS on. You can go on anyway.
  3. Your boiler: size (10, 15 or 25 kW, filled in from the boiler when it can), software version, minimum power and fan rpm at 100 %. These are the same three numbers as for Picture for service, which then does not ask again.
  4. Outside temperature (optional): pick your town. Only its rounded coordinates are sent.
  5. Pellets: how much your store or silo holds, how much is at home now, and the name on the bag (optional).
  6. Ash bin: mark it as emptied now (optional).
  7. Heating plan: warm in the morning, keep warm in the evening, both, or no plan yet. The plan is saved but stays off until you turn it on on the Plan page.
  8. Done: a short summary and Open the page. "Skip the setup" at the top also ends it.

Settings

Settings is a short list of groups. Each row shows its state in one line and opens its own small page. On a PC the list stays on the left and the group opens beside it.

  • Everyday: Heating plan (on/off and the stop and start rules), My boiler (boiler size and the numbers the boiler does not send), Pellets & ash (silo size, "buy before" reserve, ash bin size), Phone alerts, Outside temperature, Home Assistant (read-only: what the .env file says, the password only as "set"), This screen (language, theme, animations).
  • Advanced & service: Automatic alarm reset, Hot-water tank sensor, Service & relearn (Picture for service, "I cleaned the flame sensor", "Fan replaced or fan settings changed", reset the history, run the setup again), About this monitor (version, page port, days kept, and a link to this guide, which the monitor also serves at /guide, even without internet).

Changes are saved at once: a switch when you tap it, a number when you leave the field or press Enter. "Saved" shows under the field. A wrong value gets one plain line ("Type a whole number from 10 to 100.") and the old value stays in use. Turning on the heating plan or the automatic alarm reset asks first. Two places keep their own button: the period editor on the Plan page (Save) and the setup guide (Next). The classic page keeps its own Settings tab.

Security

The monitor is made for a home network you trust. It has no log-in.

  • Anyone who can open the page can use it all: start and stop, alarm reset, the heating plan and every setting. The page also shows the phone-alert topics and the phone PIN. For a page that can only look, set BURNER_REMOTE_START=0 (no start or stop from the page or Home Assistant).
  • Other websites can't use it. The page only works under the names in BURNER_ALLOWED_HOSTS, and every change needs a special header that a web page you visit can't send. So a bad web page can't read or press anything.
  • Never open a port in your router for the monitor. From outside the home, use Home Assistant's remote access or phone alerts (ntfy): both work without an open port.
  • The Wi-Fi setup hotspot pelletpi-setup has no password. It only runs while the Pi has no network, and turns off when the Pi is on your Wi-Fi.
  • The boiler's own safety stays on whatever the monitor does.

Raspberry Pi setup with SSH over the USB-C cable

The pi/ folder holds a one-time setup script for Raspberry Pi OS Lite 64-bit (Trixie), tested on a Raspberry Pi 4. It turns the Pi's USB-C port into a network cable: plug the Pi into a Windows, macOS or Linux PC and it shows up as a network adapter, with no driver to install. The Pi is then at 10.55.0.1.

  1. Write the card with Raspberry Pi Imager. In its settings choose a host name (e.g. pelletpi), a user, your SSH public key, your Wi-Fi and your time zone. Your Wi-Fi password and keys stay on your card only; never commit them.
  2. Add the USB-C network setup. Open the card's boot partition (bootfs) on your PC:
    • Copy pelletpi-setup.sh to the root of bootfs.
    • In config.txt, add at the end, under [all]: dtoverlay=dwc2,dr_mode=peripheral
    • In cmdline.txt (one single line, do not add line breaks), add at the end: 
       systemd.run=/boot/firmware/pelletpi-setup.sh systemd.run_success_action=reboot systemd.unit=kernel-command-line.target
    On the first start the Pi runs the script once, removes it from cmdline.txt and reboots. The script makes the USB-C port a network adapter that Windows, macOS and Linux recognise by themselves (RNDIS with Microsoft OS descriptors), with the Pi at 10.55.0.1 handing the PC an address. It writes pi-setup.log and, after every start, pi-diag.txt to bootfs, so you can read the Pi's status by putting the card in any PC.
  3. Connect. Plug the Pi's USB-C port into the PC (this also powers the Pi; use a strong USB-C port), wait about 2 minutes, then: 
    ssh pi@10.55.0.1
  4. Install Docker, then continue with the quick start above: 
    sudo apt-get install -y docker.io docker-compose
sudo usermod -aG docker $USER
  5. Logging for long tests (optional, recommended): 
    sudo sh pi/install-pi-logging.sh
    Writes one line of Pi health per minute to data/pi-health-*.jsonl and keeps the system journal across restarts. Works without internet.

tools/tunnel_proxy.py lends the PC's internet to the Pi through the SSH connection, for when the Pi has no Wi-Fi yet (for installing Docker).

Connecting the boiler (USB)

  • Use one USB-serial adapter. The program looks for it by itself (BURNER_PORT=auto): FTDI, CH340, CP210x and similar adapters (they show up as /dev/ttyUSB… or /dev/ttyACM…). Any USB socket on the Pi works.
  • Unplugging is fine. If the adapter is unplugged, moved to another socket, or the boiler is switched off and on, the program finds it again within a few seconds. No restart is needed.
  • More than one USB-serial adapter? The program will not guess. The log says which ones it found; put the boiler's one in a .env file next to docker-compose.yml, using its stable name, for example BURNER_SERIAL=/dev/serial/by-id/usb-FTDI_FT232R_USB_UART_XXXXXXXX-if00-port0 (list them with ls /dev/serial/by-id/). Other USB devices (keyboard, USB stick) do not matter.
  • Only one program on the boiler. Never let two programs (e.g. an old PC copy and the Pi) talk to the module port at the same time.
  • Keep the gaps short. When the boiler hears nothing from the module port for a while it shows alarm 15 "EKSTERN IO!", which has to be reset on the boiler. Updating the program takes only a few seconds: build first (docker compose build), then docker compose up -d.
  • Power. Give the Pi its own good 5 V / 3 A USB-C power supply. A weak supply shows as undervolt in the Pi health log. Do not power the Pi from J4 (see Power budget).

Running without internet

The program works fully offline; only the outside temperature waits for the internet. Two things to know:

  • The clock. A Raspberry Pi 4 has no clock battery. It sets its clock from the internet. If it restarts while there is no internet, its clock starts from where it was when it stopped, so it is behind until the internet is back. The heating plan uses this clock. The Pi health log shows clock_synced for every minute.
  • Logs for analysis. Everything is kept in ./data on the Pi (how long: see Disk use):
    FileContents
    hist-*One line every few seconds
    raw-*Every value, every second
    events-*Starts, stops, alarms
    ignitions.jsonlOne entry per ignition
    cfg_changes.jsonlBoiler settings changes (time, setting, old, new). The last 10 are on /classic → Analysis
    responder.logThe program's own log
    pi-health-*Once a minute: clock, temperature, power, Wi-Fi, internet (ping and DNS name lookup), USB adapter, container
    Install the Pi health log once with sudo sh pi/install-pi-logging.sh; it also keeps the system journal across restarts (journalctl -b -1 shows the start before, e.g. USB plug events). To take the logs home: scp -r pi@<pi-address>:pelletburner-monitor/data ./burner-data
  • A full SD card. When the monitor cannot save, the Now tab shows a short notice and the log gets one "write failed" line (and one "writes work again" line later). The monitor keeps running; history from that time is lost. Free space or use a bigger card.

Updating

On a Raspberry Pi set up with the easy install (or pi/install.sh) the monitor updates itself. Every night it looks for a new release and installs it while the burner is off or waiting. You can also do it from the page: Settings → About this monitor → Check for update. The same button is at the bottom of every page and on /classic. It also works when the nightly update is turned off.

No internet at the boiler? Share it from your phone for a few minutes.

  1. Turn on the hotspot on your phone. It must be a Wi-Fi the Pi knows: the one you gave it when you made the card, or one you added through the pelletpi-setup Wi-Fi (see Easy install).
  2. Open the monitor's page and press Check for update.
  3. Wait. The page shows each step by itself: checking, downloading (5–15 minutes), installing, testing. No internet: it says so, and you can press again.
  4. Turn the hotspot off when the page says the new version is downloaded, or when it says "Now on …".

What the Pi does, and what "went back" means:

  • Only releases are installed. The new version is made ready while the old one keeps running. The swap takes a few seconds and only happens while the burner is off or waiting (or the boiler is switched off). If the burner is busy, the Pi waits up to 6 hours; no internet is needed for that.
  • After the swap the new version is tested: it must start within 2 minutes, show the boiler's data, read your settings, and be connected to the boiler again within 5 more minutes. If one of these fails, the Pi goes back to the old version by itself and the page says "… did not work here – went back to …". That version is not tried again by itself; Try … again does it once more.
  • For 14 days after an update the page also has Go back to …, in case you do not like the new version. It, too, only runs while the burner is off or waiting. The version you left is not installed again by itself.
  • Your settings and history (the data folder) are never touched. A power cut, lost internet or a full card in the middle leaves the old version running.
  • Not installed: when you changed the program's own files on the Pi (the page says "local changes"), and at night when the Pi runs a copy cloned from a branch instead of a release, also one a few commits after a release (the button installs the release only if your copy is older). A release whose build failed 3 times is skipped until Try … again.

Turn the nightly update off with AUTO_UPDATE=no in pelletpi/settings.txt on the card. By hand on the Pi: sudo pelletpi-update now and sudo pelletpi-update back; the log is /var/lib/pelletpi/update.log (a copy is in data/update.log). A card made from this project checks the project's public repository; a card for your own copy is made with scripts/make_card.py --repo-url ….

A Pi installed before this version has the first updater: it updates, but the page shows no progress and has no Go back. Run this once on the Pi, in the program folder: sudo sh pi/install-auto-update.sh. From then on the updater follows the program by itself.

Home Assistant

The monitor can send all its values to Home Assistant over MQTT. It uses Home Assistant's own MQTT broker, the Mosquitto broker add-on.

  1. In Home Assistant: install the Mosquitto broker add-on, and make a Home Assistant user for the monitor (Settings → People → Users), for example burner.
  2. On the Pi, in the .env file next to docker-compose.yml: 
    BURNER_MQTT=homeassistant.local
BURNER_MQTT_USER=burner
BURNER_MQTT_PASS=the-password
    Use Home Assistant's address on your network if homeassistant.local is not found (add :1883 only if the port is different). Then docker compose up -d.
  3. Home Assistant finds it by itself: one device, Pellet burner, appears under Settings → Devices & services → MQTT.

What appears: state (in words and as a number), alarm (number and text), boiler temperature, outside temperature (when turned on in the monitor), flue temperature (only when a flue sensor is fitted), setpoint, power, flame, fan % and rpm, auger, igniter, ash plate, silo content, pellets left, pellets per day, days left, ash bin fill, the burner health checks, last start and its lighting time, the heating plan's next start, data age, boiler link, the monitor version, and on a Raspberry Pi: CPU temperature and load, free disk and memory, uptime, Wi-Fi signal, internet, under-voltage and USB adapter. When the monitor stops, every entity shows "unavailable".

Start and stop: Home Assistant gets Start burner and Stop burner buttons and switches for the heating plan and the auto-start schedule. The buttons follow the same rules as the buttons on the monitor's page: they only exist when start/stop is allowed (--allow-remote-start, on in the Docker setup), the command goes to the boiler on its next contact (about 30 s), and nothing is sent while the boiler is in ALARM: an alarm is always reset on the boiler or on the monitor's page. On the monitor's page, Start/Stop during an alarm first warns that it resets the alarm, and only goes ahead after you confirm. The boiler's own safety functions stay active. BURNER_MQTT_READ_ONLY=1 in .env sends values only, with no buttons or switches.

Who started it: every start and stop is saved with who or what did it: the heating plan, the schedule, Home Assistant (MQTT), the web page, the auto alarm reset, the boiler itself (minimum mode or temperature) or someone at the boiler's panel. The monitor's page shows it in Recent events, next to the state ("Started by: …") and on the "Last start" card. In Home Assistant it is the started_by attribute of Last start. The monitor knows its own commands for sure. The rest is read from the boiler's behaviour: a start out of WAITING is the boiler itself, a start out of STOPPET with no command is counted as by hand on the panel.

Hot-water tank temperature from Home Assistant: if a sensor in Home Assistant measures the hot-water tank, the monitor can pass it on to the boiler (shown there as the tank temperature, for hot-water priority). Turn the hot-water tank sensor on in the monitor's settings with source MQTT, and let Home Assistant send the number to burner/cmd/vvb every few minutes (not retained), for example with this automation:

- alias: Tank temperature to the pellet burner
  triggers:
    - trigger: time_pattern
      minutes: "/2"
  actions:
    - action: mqtt.publish
      data:
        topic: burner/cmd/vvb
        payload: "{{ states('sensor.hot_water_tank') }}"

With no reading for 15 minutes the monitor reports a safe "warm" value, so a dead sensor never makes the boiler heat. This also works with BURNER_MQTT_READ_ONLY=1. Boiler settings are never changed over MQTT.

Viewing from outside the home: use Home Assistant's own remote access (for example the Home Assistant app). The monitor itself stays on the home network.

Check the connection: python scada/mqtt_check.py --env .env listens for 40 s and checks everything the monitor sends (exit code 0 = all good).

Phone alerts (ntfy)

The monitor can send a message to your phone when something happens at the boiler. It uses ntfy: a free app, no account needed. It is off until you turn it on.

  1. Install the ntfy app on your phone (Android or iPhone).
  2. On the monitor's page: Settings → Phone alerts. In the ntfy app press +, type the topic (shown on the page, with a Copy button) and subscribe — or scan the QR code with the phone's camera to open the link. The ntfy app has no QR scanner of its own.
  3. Turn alerts on, and press Send test.

Anyone who knows the topic can read the alerts. The topic is made at random the first time (burner- + 24 random characters) and works like a password: keep it to yourself. It is not sent to Home Assistant and not written in full to the logs. New alerts topic makes another one: anyone with the old link gets nothing more, the old topic gets one last message ("Subscription ended"), and every phone has to subscribe to the new topic.

Events (each can be turned on or off; the first seven are on):

  • Boiler alarm, with the alarm's name; and when the alarm is gone. An alarm is told once, also when the monitor restarts while it is still on.
  • No contact with the boiler for 5 minutes; and when contact is back.
  • Silo low: the boiler's silo counter below a limit (50 kg by default).
  • Ash bin almost full, burner needs cleaning, or an ash-plate problem.
  • The Pi itself: disk almost full, too little power, too hot (needs the Pi health log).
  • Weak Wi-Fi for 30 minutes; or, when the internet is back, that it was down for 30 minutes or more (no message can get out while it is down). The Now tab also shows a short notice after 15 minutes.
  • Off by default: burner started, burner stopped (with who did it, e.g. “Started by: heating plan”, the same words as on the page), monitor (re)started, a short summary of the last 24 h (burning hours, starts, pellets, alarms) at a time you choose.

The same message comes at most once every 30 minutes. Messages are in the page's language (English or Danish). A failed start is not a separate message: the boiler stops with alarm 4, which is sent as an alarm. You can use your own ntfy server instead of ntfy.sh: New alerts topic sits next to the topic; the server and the certificates are in the folded part Own server and certificates.

Certificates: the connection to the server is always checked; this can't be turned off. The certificate list is kept in data/ca/. Update certificates fetches a new one from curl.se (checked with the current one; the old is kept as .bak), or you can upload a file. If sending fails with a certificate problem, check the Pi's clock first — a wrong clock breaks certificates.

Start/stop from the phone (optional, off)

Start or stop the boiler from the ntfy app, from anywhere. Set it up under Settings → Phone alerts → Start/stop from the phone: type a PIN (4–6 digits) or press Make a PIN, save it, then turn it on. The page shows the PIN (anyone who can use the page can start the boiler anyway) and warns if it is easy to guess. Alerts must be on, and remote start/stop must be allowed (BURNER_REMOTE_START=1, the Docker default).

  1. In the ntfy app, subscribe to the command topic too (a second secret topic, shown on the page with a Copy button). Then you can send to it.
  2. Tap Start or Stop on an alert, or type start or stop in the command topic.
  3. The monitor answers on the alerts: "To start the boiler reply: 4821 <your PIN> (valid 2 min)". Reply in the command topic with the code, a space and your PIN. Only then the command is sent.

Type status for a short answer (state, boiler °C, alarm, last start; no PIN needed). Anything else gets a short "Not understood" help, at most once a minute.

Anyone who knows the command topic AND your PIN can start or stop your boiler. Keep both to yourself. The monitor never sends your PIN; you type it only in your reply. The one-time code is new every time, works for 2 minutes and only once, so an old "start" message sent again does nothing. 3 wrong tries lock phone commands for 15 minutes, with an alert. The Start/Stop buttons on the alerts hold the command topic, so someone who can read your alerts can see it — they still need your PIN.

One command waits at a time. A boiler in alarm is refused (and you are told); the phone never resets an alarm. The command goes the same way as from Home Assistant or the web page, and the boiler's own safety stays on. The PIN is shown only on the monitor's own page. The monitor only listens outwards to the ntfy server (no port is opened); the command topic is not sent to Home Assistant and not written in full to the logs. New command topic makes another one.

A reading around 17 means only a little light reaches the sensor, so a dirty sensor glass pushes a real flame below the limit quickly.

The hot-water tank (VVB) temperature is not a sensor on the controller. It comes from the module on J4 (see Protocol).

Fitting a flue sensor: the input takes a type K thermocouple probe. PT100 and PT1000 flue sensors sold for other pellet boilers do not fit. A sheathed stainless probe rated to 400 °C covers the controller's range.

  • Mount it in the flue pipe about 2–3 pipe diameters after the boiler outlet, before any draft stabilizer, with the tip in the middle of the gas stream.
  • Switch on RØGFØLER under MONTØR → EKSTRA UDSTYR and read the value in the test menu.
  • If the reading falls when the tip is heated, swap the two wires.
  • With the two input terminals bridged, the reading should be about the board temperature (expected, not yet tried).

The flue temperature is not used for control. In V1.40.1 it only feeds the display and alarm 9.

Inputs and outputs

Local inputs: THERMOSIKRING (thermal safety switch, alarm 2), ASKEPLADEKONTAKT (ash plate home switch, alarm 6) and the fuse sense on hardware V3 and later (alarm 13).

From the J4 module: VVB temperature and EKSTERN START/STOP.

Outputs (as listed in TEST MENU → OUTPUTS): RØGSUGER (fan, speed controlled), SNEGL (auger), ASKEPLADE, ELTÆNDER (igniter), PUMPE (boiler circulation pump), RENSEFJEDRE (cleaning springs) and VVB PUMPE.

Temperature control in DRIFT

  1. Once a second, a PI regulator compares the boiler temperature with the set point and calculates a power level (0–100 %). The defaults are P = 5.0, I = 0.005 and D = 0 (PID in AVANCERET).
  2. The power level stays between the minimum power and MAX YDELSE.
  3. The fan follows the power level through a fan curve (settings 021–030).
  4. The auger follows it too: dose interval = calibration × 900 / (fuel g/h × power % / 100). So a wrong SNEGL AFVEJNING or fuel kg/h directly gives too much or too little fuel.
  5. When the boiler reaches the set point, it goes to PAUSESTOP: a controlled burn-out, ash plate turns and a cool-down of about 20 minutes before it can restart.
  6. With MINIMUMDRIFT active: if the power level stays at or below STOP VED % for about 60 s (no hot-water demand, no timer), the boiler burns out and waits. It restarts after PAUSE hours or at the next BOOST time, whichever comes first.

Overheat protection

As the boiler gets hotter, these act in order:

  1. Set point: the burner modulates down, then goes to PAUSESTOP.
  2. Circulation pump: PUMPE runs whenever the boiler is above its pump temperature, in every state including ALARM, to move heat out of the boiler.
  3. 155 °C: alarm 8. Meant as a sensor fault, but it is also the only software over-temperature cut-out. Alarm 1 OVERKOGNING is never used.
  4. THERMOSIKRING: the mechanical safety switch, independent of the temperature sensor. Opening it while running gives alarm 2.

In ALARM the igniter, auger and cleaning stop, the fan runs at 25 % for 2 hours to clear smoke, and the pump keeps following the boiler temperature. The alarm stays until START/STOP is pressed.

After a power cut the controller always starts in STOPPET. It never relights by itself.

Where settings are stored

  • Settings are kept in a separate flash chip, in two copies with a checksum. If the first copy is damaged at power-up, the controller uses the second. If both are bad, it loads the factory defaults for the selected KEDEL TYPE.
  • Counters (silo content, number of ignitions, operating time) are kept separately, in the processor's own flash.
  • A setting changed on the screen is saved straight away.
  • A setting changed over J4 changes the running value only. It is probably saved the next time any setting is saved from the screen, so it may be lost after a power cut (unconfirmed).

Clock and timer

  • The clock is a battery-backed clock chip. It can only be set in SÆT UR. There is no internet time sync and no way to set the clock over J4.
  • There is no weekly program. The only time-based settings are MINIMUMDRIFT BOOST 1 and 2 (minutes after midnight, 0 = off) and PAUSE.

Software updates

  • INDLÆS NY SOFTWARE only works when the boiler is STOPPET or in ALARM. Updating the controller software is a job for the dealer.
  • Updates cannot be started over J4 or WiFi. A factory reset can (see Protocol).

Alarm details

Most alarm checks run once per second. "Light" means the flame sensor value in lux, which the controller uses as its main sign of fire.

2 – BRÆNDER FRAKOBLET/SKAKT VARM!

  • Triggers when: the thermo switch input reads open while the boiler is in any running state (start-up, operation, pause or rescue), and no other alarm is active.
  • Filtering: the switch must be open for about 0.1 s before it counts.
  • Meaning: the burner or pellet shaft cut-out has tripped (too hot, burn-back risk), or the burner plug or cable is disconnected.
  • Check: burner plug and cable, thermo switch continuity, signs of burn-back into the shaft.
  • Note: real overheating shows up as this alarm. Alarm 1 (OVERKOGNING!) is never raised.

4 – OPTÆNDINGSFEJL!

Raised in three situations, all meaning the flame sensor never saw (or did not keep) more than 17 lux:

  1. Ignition never catches. The controller runs the auger for the start fuel (TÆNDBRÆNDSEL, factory 28 s) with the igniter on and the fan at TÆND LUFT. After OPVARMNING (80 s) it adds top-up doses of SUPPLERING seconds every INTERVAL (35 s), up to MAX DOSER (20). If light is still at 17 or below when TIMEOUT (factory 600 s) runs out, the alarm is raised. All of these are in MONTØR → OPTÆNDING, and an installer may have changed them.
  2. Flame lost right after ignition. In the step-up phase after the first flame, light at 17 lux or below for more than 30 s raises the alarm.
  3. Repeated dosing time-outs during start-up dosing (more than 2).
  • Check: dirty or misaligned flame sensor, igniter element, too little start fuel, wet pellets, blocked air intake.
  • Tip: watch LUX in the test menu while holding a flame to the sensor; it should rise well above 17.

5 – MANGLER BRÆNDSEL

  • Triggers when: a fire rescue (REDDER BÅL) fails to get light above 99 lux within 10 minutes, and the new start that follows 20 minutes later also fails to light. See "Flame detection and fire rescue" below.
  • Check: empty silo or pellets bridging, blocked auger or drop shaft, auger motor. A dirty flame sensor can also cause it, because a live fire then looks dark.

6 – ASKEPLADE

  • Triggers when: the ash plate still sits on its home switch 3 s after the motor starts; or it leaves but is not back home within 15 s (after one automatic retry); or, during start-up and pause, the whole ash plate job takes more than 60 s.
  • Check: ash or clinker under the plate, ash plate motor and coupling, the ash plate switch (ASKEPLADEKONTAKT) and its wiring. Full sequence below.

7 and 8 – FØLER IKKE MONT.! / FØLER DEFEKT! KEDELTEMP

  • 7 triggers when the boiler temperature reads −40 °C or lower, which is what a disconnected sensor gives.
  • 8 triggers when it reads above 155 °C, which is what a short-circuited sensor gives.
  • Checked in every state, including when stopped.
  • Check: sensor plug and cable, broken or pinched wire, water in the connector.

9 – FØLER IKKE MONT.! RØGTEMP

  • Triggers when: the flue temperature reads −25 °C or lower and the flue sensor is enabled in settings.
  • Check: flue sensor plug and cable. If no flue sensor is fitted, the setting should be off.

12 – RØGSUGER

Two independent checks, starting 10 s after power-up:

  1. Fan stopped: the fan is commanded on, but the measured speed is 0 RPM for 30 s in a row.
  2. Speed collapsing: in operation or pause only. Speed is below half of what is expected and has fallen on 5 checks in a row.
  • The boiler goes to alarm immediately. Both checks are disabled by IGNORE FAN ALARM in the hidden menu.
  • Check: fan motor and bearings, the RPM (hall) sensor and wire, soot in the fan housing. A fan that spins but shows 0 RPM points to the sensor, not the motor.

13 – SIKRING

  • Triggers when: the fuse sense input reads 0 (fuse blown). Only on hardware V3 and newer. Checked in every state; the boiler goes to alarm immediately.
  • Check: the fuse on the controller board. Find out what blew it before replacing it; the igniter and motors are the usual suspects.

14 – SNEGL AFVEJNING!

  • Triggers when: the boiler is stopped and the stored auger calibration value is 0, meaning the auger has never been weighed.
  • Fix: run SNEGL AFVEJNING / MANUEL KØRSEL and weigh the output. The alarm clears by itself once a value is saved.

15 – EKSTERN IO!

  • Triggers when: IO BOKS is enabled (AVANCERET → EKSTRA UDSTYR) and the add-on module on port J4 (the IO box, which also carries the WiFi link) stops answering the controller's polls for about 50 s.
  • Check: module fitted and powered, the J4 cable, and the RS-485 wires not swapped. If no module is installed, switch IO BOKS off in EKSTRA UDSTYR. Note that with IO BOKS off, the VVB temperature and the EKSTERN START/STOP input also disappear, because the module supplies them.
  • External start/stop: the input only matters if EXT. START/STOP is switched on in MONTØR. When it is on, an open "stop" contact keeps the boiler stopped (and stops it again after a start), and START/STOP on the screen shows "Disabled - External start/stop active". When it is off (the default), the input is only displayed in the test menu and has no effect.
  • Reset: this alarm only clears with a power cycle (off and on), even after the module answers again. Confirmed on the bench.

1, 3, 10, 11 – not used

These have screens but are not known to be raised. If you ever see one, please share it with the community, because it means this guide is wrong.

Resetting alarms

Pressing START/STOP while an alarm is shown clears it and leaves the boiler in STOPPET; it never restarts by itself. If the cause is still there, the alarm comes back within about a second.

The same reset can be done remotely over the J4 port (see Protocol). The module command service.run_mode = stop (or start) while in ALARM clears the alarm to STOPPET, exactly like the button. It does not restart the boiler; a second start then lights it. It works like the button and the factory auto-mode, and the boiler's own protections (ignition time-out, flame loss, overheat) stay active. Confirmed on the bench.

What the boiler does in alarm:

  • Igniter and cleaning output switch off.
  • The flue fan drops to 25 % and keeps running for 2 hours to clear smoke, then stops.
  • The display shows ALARM plus the alarm text.

Before you reset, look at PRE ALARM DATA in the hidden menu. It keeps a snapshot from just before the alarm: the state the boiler was in, boiler and flue temperature, lux (now, low, high), fan speed and %, seconds since the last pellet dose, doses in the last 5 minutes, and the thermo switch. The "state before alarm" alone usually tells you which part of the sequence failed.

Operating states

The controller is always in one of eight states. The number is what PRE ALARM DATA and some service tools show.

Main transitions:

  • STOPPET → OPSTART when START is pressed; WAITING → OPSTART when the timer, a temperature drop or a BOOST time says so.
  • OPSTART → OPTÆNDING → DRIFT once light passes 17 lux.
  • DRIFT → PAUSESTOP when the boiler is hot; DRIFT → REDDER BÅL on loss of flame; DRIFT → WAITING on a minimum-mode burn-out.
  • REDDER BÅL → DRIFT if the fire comes back, otherwise alarm 5.
  • Any alarm → ALARM; ALARM → STOPPET when START/STOP is pressed.

Flame detection and fire rescue

The controller judges the fire almost entirely by light, so a clean, well-aligned flame sensor matters more than anything else. Typical values are in the hundreds of lux when burning.

Light (lux)What the controller concludes
above 17Flame present: ignition succeeded, igniter switches off
17 or below for 30 s, just after ignitionFlame lost: alarm 4

10 or below for 5 minutes (cancelled if it rises above 49)Fire is going out: start REDDER BÅL
above 99 within 10 minutes of rescueFire is back: return to DRIFT
3 or below (minimum mode)Planned burn-out: 4 minutes later go to waiting

Fire rescue (REDDER BÅL) runs in three steps:

  1. Adds fuel with the auger (about 8 doses or 10 s).
  2. Runs the fan at 100 % for 10 s.
  3. Drops the fan to 60 % and waits up to 10 minutes for light above 99 lux. If that fails, it waits 20 more minutes and makes a full new start. If that ignition also fails, the alarm is shown as MANGLER BRÆNDSEL (alarm 5) instead of OPTÆNDINGSFEJL.

Recovery Alt (burn-out), from V1.40: every rescue starts a 2-hour timer. When a third rescue starts while the timer from two rescues ago is still running, the controller stops trying to save the fire and burns the cup empty instead. The screen shows RECOVERY ALT.

  1. Fuel is set to 0, so the auger stops, and the fan runs at 25 %.
  2. It waits until the light reads 0, at most 30 minutes.
  3. It waits 20 more minutes.
  4. It makes a full new start (OPSTART, then ignition).

The likely reason is that after three rescues the cup is full of unburnt pellets or clinker, and more fuel makes it worse (interpretation). Timings are for V1.40.1.

V1.40 feeds during the burn-out. The release note for V1.40.1 says the auger was stopped in Recovery Alt, so V1.40 keeps dosing for up to 30 minutes at low fan (from the release note, not checked). A board on V1.40 should be updated to V1.40.1 or 1.41.

Ash plate

The ash plate motor turns the plate one full revolution per cleaning turn, and a switch (ASKEPLADEKONTAKT) tells the controller when the plate is at its home position.

One turn, step by step:

  1. Motor starts.
  2. After 3 s the switch must show the plate has left home. If it still shows home: motor stops, alarm 6, no retry.
  3. Within 15 s of the start the switch must show home again (one full turn).
  4. If not: motor stops for 3 s and tries once more, with about 12 s more to reach home. If it still fails: alarm 6.
  5. If more turns were asked for, it repeats; otherwise the motor stops.

There are only two ways into ALARM 6: the plate never leaves home, or it does not get back home even after the retry.

When it runs:

  • One turn at every start-up (OPSTART).
  • One turn in DRIFT each time the pellets burned since the last cleaning reach ASKERENS INTERVAL (set in grams, max 60 000 g). Skipped during a minimum-mode burn-out.
  • Three turns, and later two more, during PAUSESTOP.
  • During start-up and pause the whole job must finish within 60 s, otherwise alarm 6.

Soot or coarse ash

Soot, or coarse ash with unburnt bits, usually means too little air for the pellets at low power. It is often seen after a KEDEL TYPE change to a bigger model: more pellets per hour, and a slower fan at low power. Change one thing at a time and watch for a day:

  1. Raise the 30 % point in MONTØR → SUGEINDSTILLINGER → BLÆSER YDELSE (example: 500 → 1200 RPM).
  2. Check IGNITION: start fuel back to what it was, and fewer extra doses.
  3. Only if it is still bad: lower BRÆNDSEL KG/T. This also lowers the top output.

Minimum mode and BOOST

Minimum mode (MINIMUMDRIFT) lets the fire burn out at low demand and restarts it later, instead of idling at low power.

What happens at a burn-out:

  1. The fan runs at 25 % for 20 minutes and the boiler goes to the waiting state.
  2. Two countdowns start: the PAUSE hours, and the time until the nearer BOOST time.
  3. The shorter one is shown as STARTER OM hh:mm.
  4. If PAUSE ends first, the boiler restarts straight away.
  5. If a BOOST time comes first, it restarts only if the boiler is at least 10 °C below its set point. Otherwise it shows AFVENTER TEMPERATURFALD and waits.

If the boiler shows AFVENTER TEMPERATURFALD after a BOOST time, it is not stuck: it is waiting to cool 10 °C below its set point.

The next BOOST time is worked out again at every burn-out, so BOOST 1 and 2 mean "two fixed restart times per day". There is no hidden third or fourth slot. Minimum mode does not apply while the timer program is active.

  • High confidence: alarm numbers and texts, the triggers for alarms 2, 6, 7, 8, 9, 12, 13 and 14, the lux and temperature limits, the ash plate sequence, and reset behaviour.
  • Medium confidence: the exact ignition retry sequence (alarm 4), and that alarms 1, 3, 10 and 11 are never raised.

Communication port (J4)

The controller has one port for add-on modules: J4, an 8-pin RJ45 jack. It carries RS-485 data plus power for the module.

It is not Ethernet: never plug it into a network switch, router or PC network port.

Where it is

  • On the right (low-voltage) half of the controller board, between the display ribbon cable and the thermostat connector K8. Measured on a V4 board.
  • Protection parts around it: F3 (resettable fuse, marked F100L) in the supply line, TF1 and TF2 in the two data lines, TVS diodes Z4 and Z11, and a 120 Ω termination resistor across the data pair.

The left half of the board carries 230 V (transformer, relays, fuse, the large white connectors). Switch the boiler off before plugging or unplugging anything.

Activating the port

The controller only talks on J4 when the module option is switched on:

  1. AVANCERET → EKSTRA UDSTYR → IO BOKS on. The controller restarts.
  2. Until then, the INTERNET menu shows "Slukket – EXT IO skal være aktiveret før WiFi er tilgængeligt".
  3. With IO BOKS on and nothing answering, alarm 15 (EKSTERN IO!) appears after about 50 s. That is expected and confirms the port is active.
  4. Switch IO BOKS off again when you are done, or the alarm keeps returning.

SMS BOKS in the same menu switches J4 to a different protocol (9-bit addressed RS-485). It is not described in this guide yet.

What the module provides, and which software supports it

The original J4 module (the IO box) does more than WiFi. Through J4 it supplies:

  • the hot-water tank (VVB) temperature, shown as "VVB" on the home screen and as VVB TEMPERATUR under TEST MENU → INPUTS;
  • the EKSTERN START/STOP input, shown under TEST MENU → INPUTS;
  • the WiFi link to the app, including the TILKNYT ENHED code shown as "WiFi kode".

So switching IO BOKS off also removes the VVB reading and the external start/stop.

Software versions: IO box support arrived in controller software around 2018. V1.30.15, V1.40 and V1.40.1 all speak the same J4 protocol. Older software (for example 2015 versions around V1.09–V1.10) has no IO BOKS option, so nothing will answer on J4. Check the version under INFO before buying parts.

Adapter: any USB-RS-485 adapter with an A/B (or D+/D−) pair works at 57600 baud; an FTDI-based one has been tested. The board already has a 120 Ω terminator, so leave the adapter's own terminator off if it has a switch. If you see nothing but garbage, swap A and B.

Making a cable

  • Cut one end off a standard network patch cable (T568B colours) and strip the 8 wires. Put each wire in its own lever connector (e.g. Wago 221) so nothing can short.
  • Use the orange pair for data: it is a twisted pair, which is what RS-485 wants. Use white-green for ground.
  • Cap the brown and blue pairs and keep them away from everything.
  • Any USB-to-RS-485 adapter with automatic direction control works (FTDI FT232 or WCH CH343/CH340 based). On multi-function adapters, use the 2-wire RS-485 terminals (often TX+A and TX−B), not RX+/RX−, which are for 4-wire RS-422.
  • The board already terminates the bus with 120 Ω. Leave the adapter's own termination off on a short cable.

How the pinout was found (repeat this on other board versions)

Power off, multimeter in continuity or Ω mode:

  1. Plug the cut cable into J4.
  2. Find which wires connect to TF1 and TF2 (the data protection parts) and to F3 (the supply fuse).
  3. Measure Ω between the two data wires: 120 Ω = RS-485 termination, which confirms the data pair.

Power on, IO BOKS enabled, multimeter in DC volts:

  1. Measure wire to wire, not against the board. Put the black probe on a supply wire and measure every other wire. All readings negative means the black probe is on the supply (+). The wire with the full voltage is ground.
  2. Do not use the 230 V side, PE or neutral as a reference: the low-voltage side is isolated by the transformer, and probing near the mains parts is dangerous.

Power budget for add-on modules

  • The brown pair supplies about 18.7 V through a resettable fuse of roughly 1 A, from the controller's own transformer, which it shares with the controller.
  • That is fine for a small module (an ESP32-class board through a step-down converter draws about 0.1 A at 18.7 V).
  • It is not suitable for a Raspberry Pi 4: at peak load it can draw close to the fuse's limit and may brown out the controller. Power a Pi from its own mains adapter.
  • The capacity of the +5 V pair is unknown; avoid it.

Protocol

The J4 protocol in IO BOKS mode.

In IO BOKS mode the controller talks to an add-on module over RS-485. The original module (the "IO box") gave the boiler a hot-water tank (VVB) temperature sensor, an external start/stop input and the WiFi link to the manufacturer's app. The controller is always the master; the module only answers. There are two layers: small binary register frames, and JSON text carried on register 3.

Status: confirmed on the bench with a V4 board running software V1.40, which uses the same protocol as V1.30.15. Rows marked (not tested) have not been tested yet.

Software versions

  • IO box support appeared in software from around 2018. V1.30.15 (Feb 2020), V1.40 (Mar 2020) and V1.40.1 (Dec 2020) all use this protocol.
  • Older software, for example from 2015 (around V1.09–V1.10), has no IO BOKS option and cannot talk to a module.
  • The version is shown under INFO, and in cfg_data_1 field 038.
  • Software 1.41 (Aug 2022) uses the same protocol. It reports its version as 1.41 and adds master_url to the network setup command.

JSON channel (register 3)

Every JSON message ends with the byte 0x04. A transaction works like this:

  1. The controller writes a JSON command. The module acknowledges the write.
  2. The controller reads register 3 about every 200 ms. Each read replaces whatever the controller received before.
  3. The transaction completes when one single read contains the number of messages the controller expects for that command (k below), each ending with 0x04. Splitting them over several reads does not work.
  4. After 10 s without a complete answer the transaction fails.
  5. Keep each reply short: about 105 bytes works, about 330 bytes was ignored.

Connection sequence:

  1. If WiFi details are stored, the controller sends the network setup (SSID, password, product key) and expects result OK. The introspect command is optional and often not sent at all.
  2. It sends status and expects GOT_IP. Then it counts as connected, sends cfg_data_1 once and stops sending status.
  3. While connected it sends status_info every 5 minutes (adjustable), a keep-alive every 30 s, and ConnectCode when someone presses TILKNYT ENHED.
  4. Three failed keep-alives in a row, or 150 s without a good answer, make it start over from step 1.

On the WiFi screen: "WiFi kode" is the controller's own ConnectCode, a random 4-digit number that changes with every TILKNYT ENHED attempt. Signalstyrke shows −1000 dBm when the module reports no signal strength.

What the module is: the devicedrive commands match a ready-made WiFi module, which connects to a cloud service by itself (inferred from the command names). The controller only hands data to it.

Encryption: everything on J4 is plain text, including the WiFi name, password, product key and ConnectCode. The setup command sets ssl_enabled to 1, which tells the module to use TLS towards the cloud.

Software 1.41 adds a master_url to the setup command. It points the module at a separate web service instead of the module's default cloud. A replacement module can ignore it. Whether that server still runs is not known.

Reading and changing settings

  • {"response":"OK","cfg_data":true} makes the controller send its full settings (cfg_data_1) within about 3 s.
  • {"response":"OK","cfg_chg":true} makes the controller send {"cfg_req":"now"}; answer that with the new values.
  • Any {"response":"OK","cfg_data_1":{"000":61}} reply is applied at once. Only the IDs included change.
  • Saving: a change made over J4 probably only changes the running value. It is written to the settings memory the next time any setting is saved from the screen, so it may be lost after a power cut (not yet confirmed on the bench). Read the settings back after a restart.
  • Send at most about 7 settings per reply, because of the reply size limit.
  • The controller does no range check. Only write values you have first seen it send, and never write a KEDEL TYPE (033) other than 0, 1 or 2. Read the settings back afterwards.
  • Menu screens do not refresh after a remote change. Go back to the home screen and open the menu again to see the new value.
  • A safe way to map unknown settings: set several to unusual values at once, look through the menus once, then restore all of them in one reply.
  • There is no setting for the clock, and no command to update the software over J4.

Safe use

  • Reading is safe. status_info and cfg_data_1 only report.
  • Remote start and stop are a factory feature. The original IO box and app could start and stop the boiler, and run_mode uses the same path as the START/STOP button. All protections (ignition time-out, flame loss, 155 °C, THERMOSIKRING, fan and fuse alarms) stay active.
  • Be careful with automatic restarts after an alarm. A start or stop in ALARM clears the alarm, and a second start relights. Automation that does this without anyone looking can hide a real fault (ignition, fuel, ash plate) and relight into it. Let a person see the alarm before restarting.
  • Never automate factreset. It wipes the commissioning settings, including the auger calibration and boiler type.
  • Keep set point changes inside 40–80 °C, and do not touch the hidden settings (011–013, 020–033) unless you know what they do.
  • Report a real VVB temperature, or leave it at 0.0 with VVB PRIORITET off. A false low value creates hot-water demand.
  • The boiler and flue temperatures, THERMOSIKRING and the fuse are local inputs and cannot be changed over J4.

Building your own module: checklist

  1. Answer every poll within 500 ms: register 0 with a float (the VVB temperature, or 0.0), register 1 with 1, and acknowledge every write.
  2. Never set the busy bit in an answer.
  3. Answer status with GOT_IP, the keep-alive with its two messages in one read, and everything else with {"response":"OK"}.
  4. Keep every reply under about 100 bytes.
  5. Test on a spare controller before connecting to a boiler that heats a house.

$port = 'COM3'   # change to your adapter's port
$p = New-Object System.IO.Ports.SerialPort $port,57600,'None',8,'One'

Frame decoder (Python, Windows or Linux)

The repository's burner_sniff.py is a listen-only frame decoder: python burner_sniff.py --port COM3 (or --port /dev/ttyUSB0), or decode pasted hex with --hex "7e 01 01 00 01 ... 7e". Install pyserial once with pip install pyserial.

Below is a minimal stand-alone version for reference. It checks the CRC, removes the escaping and prints each frame in plain words, including the JSON text. Save it as frame_decoder.py and run python frame_decoder.py COM3 (or /dev/ttyUSB0), or python frame_decoder.py --hex "7e 01 01 00 01 ... 7e".

import sys, struct, datetime

FLAG, ESC = 0x7E, 0x7D
TYPES = {0: "none", 1: "u32", 2: "i32", 3: "float", 4: "bytes"}
REGS = {0: "float poll", 1: "status poll", 2: "setup flags", 3: "JSON", 4: "reg 4"}

def crc16_ccitt_false(data):
    crc = 0xFFFF
    for b in data:
        crc ^= b << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x1021) if crc & 0x8000 else (crc << 1)
            crc &= 0xFFFF
    return crc

def unescape(raw):
    out, i = bytearray(), 0
    while i < len(raw):
        if raw[i] == ESC and i + 1 < len(raw):
            out.append(raw[i + 1] ^ 0x20); i += 2
        else:
            out.append(raw[i]); i += 1
    return bytes(out)

def decode(body):
    if len(body) < 6:
        return f"short frame ({len(body)} bytes): {body.hex(' ')}"
    data, crc_rx = body[:-2], struct.unpack(">H", body[-2:])[0]
    ok = "CRC ok" if crc16_ccitt_false(data) == crc_rx else "CRC BAD"
    addr, reg, flags, typ = data[0], data[1], data[2], data[3]
    payload = data[4:]
    rw = "WRITE" if flags & 0x20 else "read "
    err = " ERR/BUSY" if flags & 0x10 else ""
    txt = f"addr {addr:02x} reg {reg} ({REGS.get(reg, '?')}) {rw}{err} type {TYPES.get(typ, typ)}"
    if typ in (1, 2, 3) and len(payload) == 4:
        fmt = {1: "<I", 2: "<i", 3: "<f"}[typ]  # controller sends low byte first
        txt += f" value {struct.unpack(fmt, payload)[0]}"
    elif typ == 4 and payload:
        for part in payload.split(b"\x04"):
            if part:
                txt += "\n      " + part.decode("latin-1")
    elif payload:
        txt += f" payload {payload.hex(' ')}"
    return f"{txt}  [{ok}]"

def frames(byte_iter):
    buf, inside = bytearray(), False
    for b in byte_iter:
        if b == FLAG:
            if inside and buf:
                yield unescape(bytes(buf)); buf.clear(); inside = False
            else:
                inside = True; buf.clear()
        elif inside:
            buf.append(b)

def from_serial(port):
    import serial
    s = serial.Serial(port, 57600, bytesize=8, parity="N", stopbits=1, timeout=0.1)
    print(f"Listening on {port} at 57600 8N1 (listen only). Ctrl+C to stop.")
    while True:
        yield from s.read(256)

if __name__ == "__main__":
    if len(sys.argv) >= 3 and sys.argv[1] == "--hex":
        source = iter(bytes.fromhex(" ".join(sys.argv[2:])))
    elif len(sys.argv) == 2:
        source = from_serial(sys.argv[1])
    else:
        sys.exit("usage: frame_decoder.py PORT  |  frame_decoder.py --hex HEX...")
    try:
        for body in frames(source):
            t = datetime.datetime.now().strftime("%H:%M:%S.%f")[:-3]
            print(f"{t}  {decode(body)}")
    except KeyboardInterrupt:
        pass

Module emulator (talking back)

Listening only shows the controller's polls. To get data out of the controller, a PC or small computer must act as the module and answer (this is what burner_responder.py does). The rules are in Protocol; in practice an emulator is one loop:

  1. Read bytes from the adapter and cut frames on 7E. Undo the escaping and check the CRC.
  2. For a read of register 0, answer with a float (the VVB temperature, or 0.0). For a read of register 1, answer with 1. For any write, echo the header with no payload. Answer within 500 ms, and never set the busy flag.
  3. For a write to register 3, store the JSON text, decide the reply from its first key (see the command table), and serve that reply on the following reads of register 3. All messages of a reply go in one read, each ending in byte 0x04.
  4. Log every status_info and cfg_data_1 the controller sends; this is the boiler data.
  5. To send a command (start, stop, a setting), put it in the next {"response":"OK", ...} reply or in the first message of the keep-alive reply.

Tips:

  • Start with a spare controller on the bench, not the boiler that heats the house.
  • Write down every setting before changing any, and read them back after each change.
  • Only one program can open the COM port at a time. Close the listener before starting the emulator.
  • On Windows, the Python launcher is py; install pyserial with py -m pip install pyserial.
